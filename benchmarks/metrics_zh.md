# 性能指标

[English](metrics.md) | 简体中文 · [性能评测示例](docs/perf/README_zh.md)

先看请求成功率，再比较相同负载下的延迟和吞吐量。`metrics.json` 保存汇总，`raw_output.json` 保存逐请求记录。

## 请求指标

| 指标 | 含义 |
| --- | --- |
| Success rate | 成功请求数除以尝试请求数 |
| 端到端耗时（E2EL） | 请求耗时；成功流式请求计时到最后一个 `choices` 非空分片 |
| TTFT | 从请求开始到首个 `choices` 非空分片的时间 |
| TPOT | `(E2EL − TTFT) / (输出 token 数 − 1)`；单 token 输出为零 |
| ITL | 相邻 `choices` 非空分片的间隔，一个分片可能包含多个 token |
| 请求吞吐量（req/s） | 成功请求数除以测量时长 |
| 输入／输出吞吐量（tokens/s） | 成功请求的对应 token 总数除以测量时长 |
| 评测时长（s） | 正式测量时长，包含等待在途请求完成的时间 |
| 平均缓存输入 token 数 | 成功且报告该字段的请求中，`usage.prompt_tokens_details.cached_tokens` 的均值 |

延迟分布只统计成功请求，P50、P95、P99 分别为对应分位数。`--no-stream` 保留延迟和吞吐量，不报告 TTFT、TPOT、ITL；仅含用量统计的分片不推进流式计时。

token 数来自服务报告的用量。缺少输入或输出数量时，需要完整对应总数的汇总指标不可用。TPOT 还需要输出用量和流式计时。缓存输入 token 表示服务报告的复用数量，不是某个存储层或 KV store 的命中率。

原始 JSON 耗时使用秒。图表中的 TTFT、E2EL 使用秒，TPOT、ITL 使用毫秒。默认不重试；设置 `--max-retries N` 后，重试时间计入该次逻辑请求延迟。

## 并发与归一化吞吐量

| 指标 | 含义 |
| --- | --- |
| `max_concurrency` | 配置限额：单轮和 trace 负载约束请求数，多轮数据约束对话数 |
| `request_concurrency.peak` | 同时活跃的 HTTP 请求数峰值 |
| `request_concurrency.mean` | 请求耗时总和除以测量时长，包含失败请求 |
| Output tok/s / user | 输出吞吐量除以配置并发；不限并发时使用实测平均活跃请求数 |
| Output tok/s / GPU | 输出吞吐量除以所选部署解析得到的 GPU 数 |

每个 HTTP 轮次是一条请求。某轮失败会停止当前对话，完整对话数与成功轮次数分别统计。[混合负载](docs/perf/multi-dataset_zh.md)按数据集、模型和请求类别分组，每组均使用完整运行时长。

## 曲线

| 曲线 | 计算方式 |
| --- | --- |
| Time | 一秒完成窗口；成功请求结束时，将其全部 token 计入该窗口 |
| Cumulative | 已完成的成功请求数或 token 总数除以经过时间 |
| Request index | 按发送顺序排列的逐请求记录 |

时间曲线包含吞吐量、活跃请求数、失败率和延迟分位数。客户端曲线只覆盖本次评测流量，Grafana 和 Prometheus 服务指标覆盖到达模型的全部流量。轨迹回放另报告 `replay_delay`，即计划到达与实际发送的间隔；轨迹端到端耗时包含这一延后。

## SLO 结果

启用 `--slo-params` 后，请求成功且满足全部耗时条件才算达到服务级别目标（SLO）。失败或缺少必要计时值的请求计为不达标。

| 结果 | 计算方式 |
| --- | --- |
| 达标率 | 达标请求数除以全部实测请求数 |
| 请求 goodput | 达标请求数除以运行时长 |
| token goodput | 达标请求的输出 token 总数除以运行时长 |
| `slo_met` | 原始结果及 W&B 逐请求记录中的判定 |

一秒完成窗口使用同样定义，失败请求计入达标率分母。没有完成请求的窗口不显示达标率。整次运行按全部实测请求评分，不平均窗口达标率；重复扫描则平均各轮结果。[SLO 并发搜索](docs/perf/slo_zh.md)按聚合条件判断探测点，寻找最高实测达标请求峰值。

## GPU 分配量

Kustomize 运行在负载和 Ready 副本时间轴上记录已分配 GPU 数。`gpu_allocation.json` 保留样本及观测空档，`metrics.json` 按设备资源名报告 `gpu_seconds`、`gpu_hours` 和覆盖率。

完整运行总量需要完整观测覆盖。`observed_gpu_seconds` 仅表示部分观测覆盖的面积，不是整次运行成本。不同设备类型分别报告；分配量衡量预留容量，不是 GPU 利用率。

## 猜测解码观测

使用 Kustomize 服务且集群提供 Prometheus 时，运行报告草稿接受率、每次草稿迭代的接受 token 数、草稿和目标模型 forward 的平均 GPU 耗时，以及两阶段在合计时间中的占比。

目标模型 forward 包含批量验证，不含采样和拒绝处理。阶段耗时衡量 GPU 工作，不是请求延迟或加速比。计数器覆盖到达所选服务的全部流量。

`metrics.json` 和 W&B Summary 根据测量窗口内的计数器增量估算，并处理重置；时间曲线采用过去五分钟的速率。短运行或缺失计数器可能没有可用估算值，重复扫描则汇总可用逐轮估算的均值和标准差。

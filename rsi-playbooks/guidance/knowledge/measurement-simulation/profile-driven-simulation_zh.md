# 剖析驱动的模拟与模型失配

[English](profile-driven-simulation.md) | 简体中文 · [测量与模拟](README_zh.md) · [推理知识](../README_zh.md)

## 模拟能代替什么

设备测量建立运行时模型后，模拟器能以较低成本探索 batch 上限、并行和路由配置。但即使内核时间很准，也推不出模型未表达的执行依赖。关键是哪些决策在校准范围内可信，而不是用一个总体误差百分比为所有预测背书。

Vidur 将剖析、运行时估计和事件驱动调度分开。MLSys 2024 论文按 token、sequence 与通信划分工作：token 级成本主要依赖本轮 token 数，attention 还依赖历史长度，collective 依赖消息大小和拓扑。运行时估计器用随机森林插值测量形状，模拟器在其外组织调度与内存管理。

## 简化特征可能丢失关键区别

Prefill attention 用由 `Σlᵢ²` 得出的等效长度近似一个批次；带宽主导的 decode attention 则按总体 KV 读取建模，依赖被评估内核能有效处理长度倾斜。两批总上下文相同，仍可能在分片数、最长序列、驻留度、启动数和后端选择上不同。替换 attention 内核即使不改变模型结构，也可能让旧特征失效。

MoE 带来专家负载分布，推测解码带来接受相关的状态转换，混合注意力带来不同持久状态与调度约束。当前模拟路径若没有消费这些特征，多加测量数据也不能补上机制。核对的 Vidur README 列出特定模型／硬件支持，并另行描述 canary 工作；分支存在不代表功能已完整或已针对新模型校准。

CPU 也是失配来源。Vidur 剖析说明列出可选、依赖实现的 CPU overhead profiling，并注明尚缺文档。设备 step 越短，遗漏调度、采样、反分词和输出开销的影响越大。把 CPU 与 GPU 时间全部串行相加也不正确；真实引擎若有重叠，就需要相应依赖模型。

## 小误差会改变未来队列

若每轮低估 δ 毫秒，固定孤立序列经过 k 轮后误差可近似累积为 `kδ`。有到达流量时，完成时间变化还会改变下轮组批、KV 释放和其他请求是否排队，因此误差不再只是常数偏移。

用 M/M/1 的 `1/(μ−λ)` 示意：到达率为 90 请求／秒，把容量从 100 估为 95，就使响应时间预测翻倍。真实连续组批不服从这个模型，但它解释了接近容量时，少量服务时间误差为何可能反转配置排名。

Vidur 的静态评估使用不含调度等待、按输出长度归一化的请求执行时间；动态评估使用同样按输出长度归一化的端到端延迟，到达为实测容量 85% 的泊松流量。论文报告静态 P95 预测误差最高 3.33%，所测动态配置的归一化延迟误差低于 9%。这不是原始 TTFT、ITL 或过载服务的误差上界。其近容量分析说明了排队如何放大小预测差异，结论限定于被评估模型与引擎 fork。

## 区分两种失配的校准

若模拟器暴露相应入口，先固定实际批次序列，比较未用于拟合的形状和 iteration 时长。保留阶段、上下文分布、graph／eager、内核与并行拓扑。误差随长度倾斜或 batch 大小呈结构变化，提示运行时特征失配；随主机工作量变化的固定偏差，提示遗漏开销。平均误差接近零，也可能掩盖 prefill 和 decode 方向相反的错误。

再把同一到达负载送入真实系统和模拟器，除分位数外，比较组批、准入、KV 占用与完成顺序。时长预测准但批次不同，说明调度、内存或到达语义有偏差；中位数准但突发恢复曲线错，说明状态转换或队列敏感性有问题。

配置搜索时，只有候选间距超过观测模型误差，排序才更有依据。选择少量有希望且刻意形成对照的候选真实部署，验证排序。硬件、拓扑、运行时、内核或图行为改变所建模机制后，应重新剖析。模拟用于缩小昂贵搜索空间，真实服务执行用于确定性能和质量。

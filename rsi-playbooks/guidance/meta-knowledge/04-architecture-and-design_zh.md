# 04｜架构与方法设计

[English](04-architecture-and-design.md) | 简体中文

结合参考知识、源码和性能分析，提出自己的算法、执行方法与架构设计，通过实现和实验不断完善，最终用于真实服务。

## 读懂现有设计与技术原理

围绕准备优化的问题，读清计算过程、数据布局、调度逻辑和上下游调用，理解当前做法的原因。比较相关研究和上游实现，了解它们针对什么硬件、模型和负载作了哪些取舍。

明确任务需要保持的计算语义与质量要求，再审视现有实现中的选择：批次组成、并行维度、数据放置、阶段划分和同步方式都可能有其他设计。已有能力可以直接复用，其实现也可以针对当前问题继续改进。

## 提出并比较不同实现

围绕同一个问题，从不同层次提出方案，明确改动发生在哪里、由哪个部分负责：

- 算子与执行运行时：研究计算算法、kernel 融合、数据布局、访存复用、编译与图执行，以及主机提交和设备执行的配合。
- 推理引擎内部：研究请求批处理、token 调度、预填充与解码的执行安排、KV 管理、推测解码，以及模型并行和通信。重点是一个推理实例内部怎样组织工作。
- Foretoken 请求服务层：研究请求在多个实例之间的路由、负载均衡、缓存感知选择、排队与准入，以及不同阶段之间的请求衔接。重点是把哪些请求、在什么时机交给哪个实例。
- Foretoken 集群编排层：研究模型实例数量、资源池、扩缩容、阶段配比和异构资源配置，并与 Kubernetes 的节点调度、资源分配和服务生命周期配合。
- 跨层架构：研究 P/D、Attention／FFN 等计算分离，以及跨实例缓存与数据传输；联合设计引擎执行、请求路由和资源编排，明确各层的数据、状态与控制职责。

写清每种方案改变了什么，收益来自哪里，新增了哪些计算、存储、传输或协调。结合实际形状和有效算力、带宽估计主要成本，再通过局部实现补充关键未知。改变批量、上下文长度或硬件条件时，重新检查这些取舍。

## 从局部实验推进设计

复用诊断阶段的真实输入与参考实现，让不同候选在相同条件下执行。比较输出、运行状态和耗时，分析预期节省的工作是否减少，以及新开销出现在哪里。结果用于修改工作划分、数据布局、接口和调度，而不只是调整同一实现的参数。

先复用 Foretoken 的部署、评测、剖析和记录能力，以及适用的上游实验入口。已有能力无法满足当前问题时，再提取相应调用与必要状态，编写局部实验或临时工具。保留有用的输入构造和测量方法，供后续迭代继续使用。

有效候选接回模型和服务后，继续分析完整执行中的表现，包括批次变化、分页或循环状态、图执行、并行通信、取消与资源释放。局部收益在服务中减弱时，查清新增转换、调度和等待，继续改进集成方式。方案的实际价值由任务负载下的性能和质量结果决定。

## 两个设计例子

- 改变并行维度：长上下文、低并发解码的 query 数量较少，attention 可能缺少足够并行工作。[Flash-Decoding](https://pytorch.org/blog/flash-decoding/) 沿 KV 长度切分，各片段计算局部结果，再按归一化权重合并。由此可以继续研究切分粒度、多个 query 的共享读取和归约成本，设计适合当前形状的实现。
- 拆分计算阶段：注意力与 FFN／专家计算可能适合不同批量和资源配置。Attention／FFN 分离（AFD）将两者分开组织，需要比较权重复用、批处理效率与逐层激活传输、等待的代价。同设备批次重组、部分阶段分离和异构部署都可以作为候选。实现参考 [FastAFD](https://github.com/hao-ai-lab/FastAFD)。

初步实现并获得收益后，继续剖析优化后的系统，沿新瓶颈深化设计。例如，AFD 分离后若激活传输成为主要开销，可以研究数据布局与通信融合；传输改善后若批次等待突出，再研究跨请求合批与流水调度；随后继续分析算子效率、资源配比和请求路由。每轮都依据新结果寻找下一层机会，已经改进的设计也可以再次重构。

## 多 Agent 共同完善方案

让不同 Agent 提出替代设计、分析源码、估算成本或实现关键部分，再围绕具体实现交换意见：减少了哪项工作，新开销是否抵消收益，不同负载下是否成立，还有哪些假设可以改变？

Worker 完整负责分配问题的研究、设计、实现与实验，直接与 Advisor 讨论替代思路，无需等待他们提供方案，依据结果推进下一轮。主 Agent 综合各方向的发现，完善整体设计并协调代码整合。按[并行探索](03-exploration-and-decision_zh.md#并行探索与交流)隔离候选并复用构建与部署能力，让独立方案同时迭代；保留的改动合并后，再验证组合方案在完整服务中的表现。

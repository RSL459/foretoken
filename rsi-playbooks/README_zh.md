# RSI Playbooks

[English](README.md) | 简体中文

Foretoken 是一个面向 RSI（Recursive Self-Improvement，递归自提升）的推理基础设施框架，支持 Agent 自主修改、部署、评测和优化推理系统。

这套手册提供任务指导、实验方法与可复用经验，并持续吸收经过验证的发现，帮助后续迭代更有效地开展优化。

## 开始优化任务

克隆仓库：

```bash
git clone https://github.com/shiweijiezero/foretoken.git
cd foretoken
```

### Claude Code

在仓库目录启动一个专用于 RSI 的交互会话：

```bash
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0 claude
```

该命令仅在本次会话启用 Agent Teams，并关闭 goal 的定时检查和自动重试。在按上述选项启动的会话中粘贴以下指令；自定义任务只需替换文件路径：

```text
/goal 使用 RSI skill 和 Agent Team，按照 rsi-playbooks/tasks/qwen-decode_zh.md 完成推理系统优化并交付规定结果。主 Agent 负责构思、任务分解、反思和团队推进，具体工作交给成员；执行期间维持任务规定的有效工作人数，及时处理结果和成员的新任务请求。遵守任务的资源、时间预算和结束条件，用户要求暂停或停止时停止推进并完成必要收尾。
```

主 Agent 用同一个 goal 管理整体目标和团队推进，成员按各自职责协作。暂停时，用 `/goal clear` 结束自动续轮，再要求团队停止本任务的实验和采集进程。

### Codex

在仓库目录打开 Codex，粘贴：

```text
使用 RSI skill，按照 rsi-playbooks/tasks/qwen-decode_zh.md 完成推理系统优化并交付规定结果。主 Agent 负责构思、任务分解、反思和团队推进，具体工作通过原生 Agent 委派；执行期间维持任务规定的有效工作人数，及时处理结果和成员的新任务请求。遵守任务的资源、时间预算和结束条件，用户要求暂停或停止时停止推进并完成必要收尾。
```

Codex 按当前会话实际提供的原生委派、消息和后续任务工具执行相同角色职责，不使用 Claude 的 Agent Team 或 `/goal`。

## Agent 分工

主 Agent 初始安排以下角色，并保留成员上下文以承接后续工作：

| 角色 | 职责与数量 |
| --- | --- |
| 主 Agent | 构思与反思优化方向，不局限于易执行的参数调整；负责拆解任务、整合证据、优先级、资源、工作人数、验收与用户交付，具体执行交给成员。 |
| 方向与进展 | 1 个，提供独立的方向反思和优先级建议，编写实验总览。 |
| 代码与瓶颈分析 | 至少 1 个全局分析者；总数由主 Agent 决定，最好每个活跃方向至少 1 个，可再按阶段或假设细分。 |
| 实验审查与归因 | 按方向和候选安排独立审查者，复核行为、对照条件与收益，编写迭代记录；不自审自己实现的候选。 |
| 知识研究与探索 | 按方向安排研究者，查阅原始资料与上游实践，提出适用方法并记录发现。 |
| 实验效率监督 | 1 个，负责全部任务节点的持续 GPU 采集和定期效率分析，报告需要行动的问题。 |
| 实现与实验执行 | 明确实现、集成、部署和评测负责人，交付实际改动、原始结果与解释。 |

工作人数统计正在执行任务的分析、研究、审查和执行成员，方向与效率监督另计。主 Agent 按任务要求和运行环境上限安排有效工作，处理人数不足的原因。

成员直接交流证据，在完成或阻塞时主动请求新任务，由主 Agent 续派或调整分工。有共享任务工具时，也可在授权范围内认领就绪任务。实验总览和迭代记录各有指定作者，主 Agent 验收成果。恢复任务时，沿用原预算与记录，并补建缺失成员。

## 设计目标

- 快速部署：将代码改动快速更新到目标集群中的推理服务。
- 测试与反馈：验证性能、模型质量和资源开销，了解改动效果。
- 观测与诊断：结合日志、指标和性能剖析，定位运行问题与性能瓶颈。
- 实验记录：关联每轮改动、运行配置、结果和决策，方便比较与复现。
- 参考与经验积累：查找、补充参考资料，将实验经验整理为可复用的指导。
- 行为与归因检查：检查模型实际行为，识别指标投机，判断收益是否确实来自预期改动。

## 使用步骤

一轮迭代以一个候选改动为单位，从部署、完成必要的性能对照、分析结果，到作出保留或回退决定。同一候选在不同负载和并发下的测量属于同一轮。

1. 明确要改善的行为和判断标准，例如降低给定负载下的首 token 延迟，同时保持回答质量。
2. 确定优化范围：聚焦路由、推理引擎等具体部分，或面向整个系统，不限定组件。
3. 阅读代码、查阅相关研究和实践，结合已有测量了解系统现状；必要时补充测量。
4. 分析问题成因与改进空间，提出自己的假设并设计方案，说明预期效果，选择能验证假设的负载与指标。缺少可比结果时，先测量改动前的表现。
5. 修改代码或配置，按[源码部署流程](../docs/custom-deployment_zh.md)更新推理服务。
6. 执行选定的[评测](../benchmarks/README_zh.md)，比较改动前后的结果，结合模型输出、日志和性能剖析判断差异来源。
7. 由独立审查者复核实现和原始结果，检查测试取巧、模型行为变化和对照条件，判断收益归因及必要的补测。
8. 按[实验记录手册](experiment-records_zh.md)保存运行记录、结果解释与审查结论。
9. 根据结果保留、调整或回退改动，再选择下一轮要解决的问题。将可复用的发现补充到指导和参考资料中。

## 选择评测

按本轮优化目标选择评测。命令选择和记录参数见[实验记录手册](experiment-records_zh.md)。

| 评测目的 | 工具与命令 | 查看内容 |
| --- | --- | --- |
| 比较延迟、解码速度和吞吐 | [性能评测](../benchmarks/docs/perf/README_zh.md)，`foretoken perf` | 成功数、延迟分布、TPOT、吞吐及实际输出长度 |
| 评估回答质量 | [质量评测](../benchmarks/docs/eval/README_zh.md)，`foretoken eval` | 得分、样本数、评分方式和逐题回答 |
| 定位计算、通信和等待开销 | [性能剖析](../benchmarks/docs/profile/README_zh.md)，`foretoken perf --profile` | 执行时间线；速度对比另用不带剖析的运行 |
| 比较不同并发、输入长度和流量下的表现 | [参数扫描与负载配置](../benchmarks/docs/recipes_zh.md) | 各负载点的指标及变化趋势 |

命令选项可用 `foretoken perf --help` 和 `foretoken eval --help` 查询。

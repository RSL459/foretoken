# 测试规范

[English](testing.md) | 简体中文

运行与改动相关的已有检查和真实场景。Foretoken 只为关键产品特征维护少量测试，代码修改不要求新增测试。

## 运行相关检查

在仓库根目录执行：

| 修改范围 | 验证 |
| --- | --- |
| 仓库文件与文档 | `pre-commit run --all-files` |
| Rust 数据面 | `make verify-data-plane` |
| Go 控制面与生成产物 | `make -C control-plane verify` |
| Python CLI | 安装包、查看受影响的帮助，并在 Kubernetes 上实际执行改动后的命令 |
| 评测 | 按[评测指南](../../benchmarks/README_zh.md)，使用真实服务来源执行受影响的命令或运行流程 |
| Helm 与 Kubernetes 配置 | lint、渲染受影响的模式，再实际执行改动后的部署路径 |

Helm 的基础检查：

```bash
helm lint deploy/charts/foretoken --kube-version 1.36.3
helm template foretoken deploy/charts/foretoken --kube-version 1.36.3 > /tmp/foretoken.yaml
```

部署执行参照 [k3d](../k3d-deployment_zh.md) 或 [Kubernetes](../kubernetes-deployment_zh.md) 指南。编译、渲染、dry-run 和只有 API server 的环境分别验证各自的边界，不代表推理服务可用。模型质量与性能结论需要明确负载和硬件条件的评测或测量，不能用固定的一句生成文本判断。记录实际命令、执行条件、结果和重要的未执行检查；缺少依赖或设备意味着场景未运行，不算通过。

## 选择并实现场景

例如，多模型服务场景通过 CLI 部署维护中的配置，分别向两个模型发送请求、检查响应，再删除部署。它检查用户能力，而不是手工构造路由表后断言字段。这个例子说明如何选择场景，不要求新增测试。

先确定特征和可观察结果，阅读实现、所属文档和已有验证，再运行相关场景。支持的行为变化时，调整已有场景的输入、调用和结果，保留其目的。

新增文件、用例、subtest 或独立场景前，即使放在旧测试中，也须取得维护者对特征范围、覆盖缺口和反复执行价值的明确认可。新增功能、修复 bug、重构或排查不自动构成永久测试的理由，一次验证可以只留下执行证据。不为测试方便扩大公共 API 或添加生产代码的测试专用开关。

选择少量代表性场景，不按函数、文件、分支、参数组合或所有可能故障列清单，不以覆盖率或测试数量为目标。不保留 getter、字段透传、常量映射、薄包装、私有 helper、框架接线或上游内部实现的测试。选定特征依赖 Foretoken 与上游协作时，验证真实接入路径。

使用真实组件和依赖，优先走完整用户路径：

- 不使用 mock、fake client、stub server、伪造引擎响应或 monkeypatch 替代生产依赖。Fixture 可提供输入、配置或准备真实资源，不实现第二套组件或模拟器。
- 复用实际 CLI、服务、Kubernetes 组件、推理引擎、硬件，以及维护中的安装、部署、请求、评测和清理路径。测试编排负责准备、执行、断言、诊断和回收，不另写安装器、控制器或请求执行器。
- 局部验证也须执行真实实现，并说明较窄的范围。
- 断言响应、配置生效、服务状态、有关指标和清理等可观察结果。检查资源语义字段，不锁定文本次数、JSON/YAML 排版、私有调用次数、偶然顺序或完整日志快照；不复制被测实现来计算预期值。
- 相关断言保持内聚，独立特征便于分别诊断。非平凡测试按特征或行为命名，并在前面用简短注释说明目的。
- 隔离可变资源，用有界等待观察完成，成功、失败和取消后都清理本次拥有的资源。诊断只保留有用内容，不包含凭据或敏感请求。

组件测试放在所属 package，按行为命名，不镜像私有模块结构。Rust 使用 crate 根目录的 `tests/`，不放入 `src/` 内联模块；Go 和 Python 使用标准 package 测试位置。跨组件 E2E 编排归属特征的验证入口，不为单个场景建立通用框架或目录体系。

## 长期保留前审查

第一轮检查正确性和执行真实性。从入口追踪真实生产者、消费者和清理，查看实际响应、状态与日志。

核对源码、依赖和产物是否对应当前改动，断言能否区分预期特征结果与具体错误，而不只是进程启动、资源存在或配置复制。

检查隔离、有界等待及失败、取消后的清理。恢复特征应在隔离的真实系统中触发对应故障。历史运行或另一条安装路径不是本次证据。

第二轮独立检查范围和维护成本。确认测试仍服务于有实际使用者的关键特征，且不能由其他场景在保留含义的前提下覆盖。

删除重复断言、穷举矩阵、无关快照、未使用 helper、失效调试脚本和 fixture，以及没有使用者的测试专用依赖。

共享准备保持简单，复用产品生命周期；不改变特征的普通重构不应迫使测试重写。缺少测试本身不是审查问题，产品缺陷应独立指出，不自动要求新增永久测试。

偶发失败应区分产品、测试或环境原因，修复或明确隔离，不通过重试或更长 sleep 换取通过。删除临时排查代码，记录实际结果。是否安排 CI 执行按 [CI 规范](ci_zh.md) 单独决定。

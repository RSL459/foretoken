# 执行 RSI 任务

[English](SKILL.md) | 简体中文

使用当前 harness 的原生委派、消息和完成通知。Claude Code 交互会话采用 Agent Team，由用户设置主 Agent 的单个 `/goal`；Codex 使用当前可用的原生 Agent 工具执行相同角色约定。派工前核对会话能力：普通子 Agent 与 Agent Team 不同，Codex 也不具备 Claude 的 Team 或 `/goal` 接口。不启动另一个 Agent CLI，不修改设置来开启团队，不添加自定义 hook 或主 Agent 周期提醒。

## 明确任务

阅读仓库指令、用户提供的任务、[共用流程](../../../rsi-playbooks/README_zh.md)、[执行规则](../../../rsi-playbooks/tasks/README_zh.md)和相关历史实验记录。成员按当前问题从[优化指导](../../../rsi-playbooks/guidance/README_zh.md)选读参考资料与已有经验。相对链接以本 skill 目录为基准。任务参数由任务文件提供，不在 skill 中复制默认值。

以历史保留方案和可比结果为起点，承接已排除的方向与未解决的问题。现有候选耗尽时，重新反思方向、研究新方法，而不是自动结束任务。方法根据目标、证据和剩余预算自主选择，完成仍以任务结束条件为准。

先判断用户要求的是执行、恢复、暂停还是讨论。暂停、停止或设计讨论不授权启动实验。新任务在实验笔记中记录起始时间与截止时间；恢复时先读取原预算与资源归属，沿用约定的时间预算。

把任务列出的全部节点纳入实验安排，确认可用资源和现有使用者，按需求分配独立候选。未使用的节点记录具体阻塞并处理可解决的问题。区分整个资源池与单服务上限。

使用 W&B 时，在并行运行前统一易读的命名。`--wandb-project` 对应长期共用的项目，`--wandb-group` 归集本次优化任务的对照，`--wandb-run-name` 标明候选、负载、并发和重复测量次数。需要区分任务时，在 group 中包含模型、硬件及任务日期或标识。不同 Worker 的可比运行放在同一 project 和 group，恢复任务沿用原命名。在实验总览中记录名称和链接，方便 Worker 与 Recorder 查找同一组结果。

## 组建团队与派工

主 Agent 负责理解目标与约束、构思整体方案、拆解和排序任务、整合证据、反思结果、调整方向、协调资源与人数、验收和交付。Worker 持续负责优化方向直到形成结论，按需与 Researcher、Recorder 协作。主 Agent 可参与具体执行，同时保持对整体方向、派工和资源协调的关注。

主 Agent 主动构思和修正优化方向，而不只是分配已有待办。把成员的局部发现联系成系统层面的理解，考虑其他解释，判断哪些问题值得深入。借助方向顾问的独立视角反思当前方案，主动推进有价值的问题，不等用户提供下一想法；方法和投入由任务决定。

开始执行时，将以下协作角色分配给原生成员。相关任务复用成员上下文，每次派工明确问题与交付。提供[共用角色约定](roles/common_zh.md)、角色文件、任务、适用仓库规范、原始证据和输出位置的绝对路径，并说明范围、截止时间、资源权限、依赖、写入负责人、成员通信地址和返回或停止条件。要求成员亲自读取这些资料。

| 角色指令 | 初始安排与人数 | 记录归属 |
| --- | --- | --- |
| 主 Agent | 自主构思、反思整体方案，协调团队，也可亲自执行。 | 与指定作者协调，负责验收和用户交付。 |
| [方向与进展](roles/direction_zh.md) | 1 个独立顾问，反思方向与进展，提出优先级建议。 | 实验总览中的优先级、未决问题、迭代链接和主 Agent 决策。 |
| [Worker](roles/worker_zh.md) | 主力执行角色，完整负责方向的代码与瓶颈分析、设计、实现、集成、部署、测量和结果解释，直到形成结论。至少 1 个 Worker 跟进系统整体执行路径；每个活跃方向优先安排一个或多个专门 Worker，主 Agent 按有效任务和资源决定人数，不以 GPU 组数决定 Worker 总数。 | 向 Recorder 和总览作者提供改动、原始证据和自身分析。 |
| [Recorder](roles/recorder_zh.md) | 按方向和候选独立检查 Hack（针对评测取巧）、对照条件和收益归因，不自审自己实现的候选。 | 指定迭代记录，以及与 Researcher 协作沉淀到 `rsi-playbooks/guidance/` 的可复用发现。 |
| [Researcher](roles/research_zh.md) | 研究方向与瓶颈问题，提供机制证据，直接与 Worker 协作。 | 指定研究笔记，以及与 Recorder 协作维护的可复用指导。 |
| [团队效率监督](roles/efficiency_zh.md) | 1 个，负责整个团队的工作效率和资源利用效率，包括任务交接、重复劳动、等待阻塞、有效并行和 GPU 持续采集。 | 采集记录，以及提供给实验总览作者的证据。 |

给 Worker 分配完整方向任务，不默认将分析转交给另一名实现者。成员可按需承担专项协作，明确集成、资源与文件归属。每项资源生命周期有明确负责人，每个文件或划分清楚的章节只有一个写入负责人。

执行期间，主 Agent 持续维护实际工作人数和有效任务，最小、最大人数从任务读取。Worker、Researcher 和 Recorder 仅在开展分配工作时计入；方向与效率监督额外安排。等待、阻塞和已完成成员不算正在工作。交接或依赖变化时，通过原生任务状态与消息核对；缺少证据的时段标为未知，不据此宣称精确活跃数或时间加权平均值。遵守 harness 上限、任务预算和用户停止要求。有效工作不足时报告真实阻塞。暂停或终止任务时停止人数维护，完成仍以优化结束条件和规定交付为准。

有原生共享 Task 工具时，主 Agent 创建工作项与依赖，指定负责人，或授权成员在约定范围和资源内认领就绪且无人负责的任务。没有 Task 工具时，成员直接请求任务，由主 Agent 明确分配，不另建队列、注册表或定时器。成员可直接交流证据、讨论不同判断，并向主 Agent 报告阻塞以及涉及优先级、资源变化的建议。

重启后读取实验记录、原预算、资源与进程归属和原生任务状态，确认哪些成员仍存在。harness 未恢复的成员重新创建，并重新分配未完成工作；保留原笔记和预算，不把保存的成员名称当作仍在运行的证据。

## 并行 worktree

并行代码改动和实验候选使用独立 Git worktree。可按成员划分，也可由一个候选组共享工作区并明确文件归属。只读调研和审查可直接读取对应 worktree。主 Agent 通过原生 Git 工具协调创建，在已有实验总览中记录基线、分支、绝对路径、负责成员、资源分配和结果位置。

把实际 checkout 与证据路径交给成员。编辑、构建、部署和验证都针对该 checkout 执行。并行实验通过已有部署机制使用独立的部署身份、可写运行缓存和结果目录，适用时复用只读模型数据。Worktree 隔离源码改动，实验并行数量由任务资源分配决定；GPU 数与实验组数从任务读取。

测量或审查前，确认候选的实际源码和运行配置，包括未提交改动。审查者读取对应候选，而非主 Agent 的工作区。决定保留后，安排合入约定分支、解决相互影响并验证集成结果。协调共享 Git 操作：worktree 的索引独立，分支和 stash 属于同一仓库。

候选改动和证据已保存或明确放弃，且成员、构建和服务都不再使用后，再删除实验 worktree。暂停时保留未完成工作，恢复时明确复用或重新分配工作区。

## 推进迭代

每个成员完成或阻塞时，按[共用角色约定](roles/common_zh.md)主动提交结果、证据、下一步建议和新任务请求。主 Agent 回应续派或重分配、确认获授权的自行认领，或明确等待依赖、暂停、结束。相关工作复用原成员上下文。原生通知和消息负责交接，goal 或任务状态本身不保证自动认领、依赖唤醒或立即补位。

1. 为 Worker 分配不同的方向任务，为 Researcher 分配支撑这些方向的研究问题。Worker 自主设计并执行方案，直接与 Researcher、方向顾问讨论机制、证据和候选；主 Agent 整合发现，调整优先级与资源。
2. 运行结束后，Worker 把实际改动、命令、运行身份、原始结果和自身分析交给独立的 Recorder。Recorder 直接向 Worker 返回审查发现与补证据请求，Worker 继续完成分析和必要对照。审查期间主 Agent 继续推进独立工作。
3. 将审查发现交给跟进整体执行路径的 Worker 和相关 Researcher，重新判断瓶颈与适用性。主 Agent 决定保留、调整或回退，负责该方向的 Worker 落实决定，继续跟进距目标的差距。Recorder 编写迭代记录，并与 Researcher 将可复用发现写入 `rsi-playbooks/guidance/`；方向顾问更新总览。
4. 假设被推翻、候选耗尽、重要依赖阻塞或支线消耗较多时间时，重新审视方向。主 Agent 与方向顾问、Worker、Researcher 共同反思证据，安排下一项有价值的调查。收到效率监督的行动性发现后，分配任务或调整资源，并告诉相应成员需要观察的结果。

沿用现有实验与迭代记录。指定作者整合证据，避免并发覆盖；独立审查保留执行者分析并单独注明审查结论。主 Agent 参与写作时与负责人协调。每次交接落到有效任务或真实的等待、终止决定，不靠反复查询状态来凑人数。

## 采集 GPU 使用情况

在每台 GPU 主机上使用本 skill 的 `scripts/gpu_usage.py`，需要 Python 3.11+ 及已安装的 `nvidia-smi` 或 `mx-smi`。脚本只依赖标准库；主机没有 checkout 时只需复制该脚本。使用现有远端任务管理器或本任务专属的持久 shell 会话，让采集在监督者分析期间及 SSH 断开后继续运行。

在各主机的仓库根目录，将 `GPU_RUN` 设为实验结果下的新运行目录，`GPU_INDICES` 设为该节点分配给本任务的宿主 GPU 序号（逗号分隔），`DEADLINE` 设为带 UTC 偏移的绝对 ISO 截止时间。启动一次：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py collect \
  --output "$GPU_RUN" --gpus "$GPU_INDICES" --deadline "$DEADLINE"
```

采集器打印 PID 和输出目录，此后默认每 10 秒向 `samples.jsonl` 追加数据。用 `--interval` 调整采样间隔。脚本自动选择已安装的设备工具；两种工具都存在时，用 `--backend nvidia` 或 `--backend metax` 指定。仅在任务拥有全部可见 GPU 时省略 `--gpus`，仅在任务没有时间预算时省略 `--deadline`。已有采样文件不会被覆盖，恢复采集使用新目录。

定期分析时，将 `WINDOW_START`、`WINDOW_END` 设为下一个已完成窗口的 ISO 时间。可在原主机、共享存储或监督者机器上的记录副本中读取数据；汇总不会启动或中断采集：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py summarize "$GPU_RUN" \
  --since "$WINDOW_START" --until "$WINDOW_END"
```

传入多个运行目录，可汇总多个节点的同一时间窗口。JSON 包含逐 GPU 和逐节点的时间加权利用率、采样覆盖、零利用率秒数、最后采样时间和查询错误。每条读数最多覆盖一个采样间隔，未覆盖时段保持未知；均值需结合覆盖率和数据新鲜度判断。零利用率反映设备活动，不直接决定此刻是否应有实验运行。

在采集主机上请求停止：

```bash
python3 -I .agents/skills/rsi/scripts/gpu_usage.py stop "$GPU_RUN"
```

停止标记、截止时间、SIGINT 或 SIGTERM 会使采集在当前查询完成后退出，查询最长 10 秒。确认最后的 `end` 记录及进程退出，再释放采集器。保留原始数据用于实验报告；恢复时使用新目录。不向已复用的 PID 发送信号，也不停止共享监控。

## 暂停与结束

用户暂停、停止和任务截止时间优先于排队消息、新任务请求及人数目标。停止安排实验，通知成员，由资源负责人停止进程并确认退出，必要时使用原生取消操作。暂停时保留可恢复的工作；完成时，在保存证据后安排清理已无使用者的资源。

按[实验记录手册](../../../rsi-playbooks/experiment-records_zh.md)，由指定作者在任务要求的路径完成交付。主 Agent 验收并汇总保留改动、实测结果、GPU 采样覆盖和未解决的阻塞。角色指令和历史验证记录不作为当前团队、实验或监督已运行的证据。
